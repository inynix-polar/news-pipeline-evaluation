# Оценка сохранённых результатов новостного пайплайна

Небольшой полностью офлайн-проект. Он читает уже готовые ответы двух версий
пайплайна, сравнивает их с эталоном, отдельно проверяет модель-судью против
человеческих решений и отвечает на вопрос: можно ли заменить `current` на
`updated`.

Никакие модели, API и исходный новостной пайплайн не запускаются.

## Как это работает за две минуты

В папке `data/` лежат три файла:

- `goldens.jsonl` — «ответы в конце учебника»: новости и правильные сущности;
- `pipeline_outputs.jsonl` — уже сохранённые ответы `current` и `updated`;
- `judge_outputs.jsonl` — уже сохранённые оценки судьи и человеческий ответ
  `reference_pass`.

Проект выполняет две независимые проверки:

```text
current / updated outputs ── сравнение с goldens ── качество пайплайнов

judge_score ── порог критерия ── сравнение с reference_pass ── качество судьи
```

Затем он сравнивает метрики `updated` и `current`, учитывает технические ошибки
и формирует итоговую рекомендацию.

Важно: оценки судьи не используются вместо golden-разметки. Мы проверяем
пайплайны по `goldens`, а самого судью — по `reference_pass`.

На пальцах: если эталон ждёт «Газпром» и пайплайн нашёл «Газпром», это
совпавшая сущность (`E_TP`). Не нашёл — пропуск (`E_FN`). Выдумал лишнюю —
`E_FP`. У совпавшей сущности затем проверяются роль, A, C и итоговое
решение. Так проходят все 24 новости для обеих версий.

После одной команды появляются:

- `report.json` — все счётчики, метрики, ошибки и расхождения;
- `conclusion.md` — короткий человекочитаемый итог.

## Быстрый запуск

Требуются Python 3.11+ и `uv`.

```bash
uv sync
uv run python -m news_eval
```

Ожидаемый финал команды:

```text
integrity: passed
current strict evaluation: failed
updated strict evaluation: failed
updated can replace current: no
```

Другие пути можно указать явно:

```bash
uv run python -m news_eval \
  --data-dir data \
  --report report.json \
  --conclusion conclusion.md
```

Тесты:

```bash
uv run python -m unittest discover -s tests -v
```

Runtime-зависимостей нет.

## Что именно считается

Для каждой версии пайплайна:

1. Проверяются строки, ключи и связи между тремя JSONL.
2. Golden и actual-сущности строго сопоставляются один-к-одному.
3. Считаются `E_TP/E_FN/E_FP`, `S_TP/S_FN/S_FP`, обязательные метрики и
   матрица ошибок ролей.
4. Явные и скрытые структурные ошибки фиксируются, но не останавливают весь
   расчёт.
5. Четыре метрики сравниваются с заданными порогами без предварительного
   округления.

Для судьи его score превращается в `pass/fail` по порогу критерия, после чего
сравнивается с человеческим `reference_pass`. Отдельно считаются правильные и
ошибочные принятия/отклонения для каждой версии и каждого критерия.

## Неочевидные, но важные правила

- Метрики считаются из общих счётчиков по 24 кейсам, а не усредняются по
  отдельным новостям.
- Matching использует только golden `name` и явно заданные `aliases`. Никакого
  fuzzy matching и самостоятельно придуманных сокращений.
- Пропущенная положительная сущность — ошибка решения и `S_FN`; пропущенная
  отрицательная сущность — правильное отрицательное решение, но всё равно
  `E_FN`.
- Лишняя положительная сущность даёт `E_FP + S_FP`; лишняя отрицательная —
  только `E_FP`.
- Невалидные A или C всегда ломают решение. Невалидный B только записывается
  как ошибка поля и не влияет на решение.
- `status=error` и не-массив `actual_output.entities` — технические ошибки.
  Корректный пустой `entities: []` — не ошибка.
- Массив `entities` с не-объектом трактуется как техническая ошибка всего
  результата.
- Лишняя сущность с невалидными A/C остаётся `E_FP`, но не получает
  положительного решения.
- JSON-число `1` допустимо как `1.0`; `true` и строка `"1.0"` недопустимы.

Для итогового `can_replace` принято прозрачное консервативное правило:
`updated` должен пройти все четыре заданных порога и не добавить новых
технических ошибок относительно `current`. Это не новый числовой порог, а
явно зафиксированная политика релизного вывода.

## Где смотреть результат

В `report.json` основные разделы такие:

- `integrity` — корректность трёх входных файлов;
- `pipeline_evaluation.versions` — результаты `current` и `updated`;
- `pipeline_evaluation.comparison` — дельты и рекомендация о замене;
- `judge_evaluation` — сравнение судьи с человеком.

Для быстрого ознакомления достаточно открыть `conclusion.md`.

## Структура проекта

```text
data/                  # три исходных JSONL без изменений
news_eval/
  readers.py           # чтение и проверка целостности
  matching.py          # строгая нормализация и matching
  evaluation.py        # метрики пайплайнов и аудит судьи
  reporting.py         # report.json и conclusion.md
  __main__.py          # CLI
tests/                 # компактные unit- и end-to-end тесты
pyproject.toml
uv.lock
report.json
conclusion.md
```
